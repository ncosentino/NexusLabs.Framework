# NLF0024 — Do not copy a rented span handle

**Severity:** Warning · **Category:** Usage · **Code-fix:** No

`RentedSpan<T>` (namespace `NexusLabs.Framework.Buffers`) is a zero-allocation `ref struct` handle
over an array rented from an `ArrayPool<T>`. Its `Dispose` returns the array to the pool. Because it
is a value type, copying one copies the field that references the underlying array — so a copy is a
*second owner of the same rented array*. Dispose both copies and the array is returned **twice**; the
pool can then hand that one array to two unrelated renters, who silently overwrite each other''s data.

`RentedSpan<T>` is **move-only**: bind one to a single `using` and use it in place, passing the view
(`.Span`, `.Array`) — not the handle — to other methods. This analyzer flags the copy patterns the
compiler allows.

> **Async / owned buffers:** to hold a buffer across `await`, use `RentedMemory<T>` — the
> reference-type owner. Copies of it copy a *reference* to one shared owner, so returns stay correct
> by construction. `RentedMemory<T>` is **not** flagged by this rule; there is nothing to guard.

## Why a `ref struct` makes this rule complete

The compiler already forbids every *heap escape* for a `ref struct` as a hard compile error — it
cannot be boxed, stored in a class field, captured by a lambda, placed in a collection, or held
across `await`/`yield`. Those are not this analyzer''s job; they simply do not compile. What remains
is copying within a single method''s dataflow, which the analyzer covers completely.

## Bad — copied into a second variable

```csharp
using var a = ArrayPool<byte>.Shared.RentSpan(64);
var b = a;        // NLF0024: b and a now own the SAME array
b.Dispose();      // returns the array
                  // 'using' disposes a at scope exit → returns the SAME array again
```

## Bad — `using var b = a;`

```csharp
using var a = ArrayPool<byte>.Shared.RentSpan(64);
using var b = a;  // NLF0024: both 'using's dispose the same array → double return
```

## Bad — passed by value

```csharp
void Fill(RentedSpan<byte> buffer) { /* ... */ }

using var a = ArrayPool<byte>.Shared.RentSpan(64);
Fill(a);          // NLF0024: 'a' is copied into the parameter; two owners
```

## Bad — defensive copy through `in`

```csharp
void Prime(in RentedSpan<byte> buffer)
{
    buffer.Dispose();  // NLF0024: 'buffer' is a readonly reference and Dispose is not
                       // readonly, so the compiler disposes a SILENT COPY — the caller's
                       // handle is left owning an array that was already returned.
}
```

## Good — use it in place under one `using`

```csharp
using var buffer = ArrayPool<byte>.Shared.RentSpan(64);
var read = stream.Read(buffer.Span);
Process(buffer.AsSpan(0, read));
```

## Good — pass the view, not the handle

```csharp
void Fill(Span<byte> destination) { /* ... */ }

using var buffer = ArrayPool<byte>.Shared.RentSpan(64);
Fill(buffer.Span);   // pass the view
```

## What the analyzer flags

Every read of a `RentedSpan<T>` handle that materializes a second value:

- an assignment right-hand side, or a variable initializer (`var b = handle;`, including
  `using var b = handle;`)
- a by-value argument
- a ternary branch (`cond ? handle : other`) or a switch-expression arm
- returning a `using`-bound handle (`using var h = ...; return h;`) — the `using` disposes it, so the
  returned value is a double consume
- invoking a non-`readonly` member (e.g. `Dispose()`) through an `in`/`ref readonly` handle — a
  silent defensive copy

## What it does NOT flag

- by-reference uses — the receiver of a member or element access (`handle.Span`, `handle.Array`,
  `handle.Dispose()`, `handle[0]`); a `ref`/`in`/`out` argument; an assignment target; a `using`
  resource; a `nameof` operand; an `is` pattern; a discard (`_ = handle`)
- a fresh acquisition bound to a `using` — `using var b = pool.RentSpan(n);`
- a bare `return handle;` of a non-`using` local — an ownership-transfer move (the caller takes over
  disposal)
- any use of `RentedMemory<T>` — the reference-type owner is copy-safe by construction

## Limitations

The rule is complete for verifiable code compiled with the analyzer enabled. It cannot see copies
made through `unsafe`/pointer code, which is the language''s explicit opt-out of safety (a `ref
struct` cannot be reached by reflection because it cannot be boxed).

## When to suppress

For a deliberate ownership transfer the analyzer can''t prove safe, suppress with a reason:

```csharp
#pragma warning disable NLF0024 // ownership intentionally handed to the pool manager
_pending = buffer;
#pragma warning restore NLF0024
```

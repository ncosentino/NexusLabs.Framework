# NLF0028 — Do not override `CreateTimer` on a fake time provider

**Severity:** Warning · **Category:** Usage · **Code-fix:** No

A class deriving from
`Microsoft.Extensions.Time.Testing.FakeTimeProvider` declares an
`override` of `CreateTimer` whose body never calls
`base.CreateTimer`.

A fake clock fires a timer when the test advances the clock past
its due time. **That scheduling is the mechanism under test.** An
override that returns a different timer — most commonly one that
invokes its callback immediately so a test "does not have to wait"
— makes every delay in the system under test complete on its own
schedule.

The consequences are worse than a slow test:

- Tests pass without ever exercising the delay.
- Ordering bugs that only appear when a delay actually elapses stay
  hidden.
- The failure is **silent**. Nothing reports that virtual time
  stopped applying, so the suite looks green and fast.

## Bad — the timer fires on its own

```csharp
// ❌ NLF0028 — a one-minute delay now completes without the clock moving.
public sealed class ImmediateFakeClock : FakeTimeProvider
{
    public override ITimer CreateTimer(
        TimerCallback callback,
        object? state,
        TimeSpan dueTime,
        TimeSpan period) => new Immediate(callback, state);

    private sealed class Immediate : ITimer
    {
        public Immediate(TimerCallback callback, object? state) => callback(state);

        public bool Change(TimeSpan dueTime, TimeSpan period) => true;

        public void Dispose()
        {
        }

        public ValueTask DisposeAsync() => ValueTask.CompletedTask;
    }
}
```

## Good — observe without replacing

Observing registrations is legitimate and does not require
replacing the timer. Call the base, record what you need, and
return a wrapper that forwards `Change`, `Dispose`, and
`DisposeAsync` to the timer the base created:

```csharp
// ✅ no diagnostic — the base scheduler is still in play.
public sealed class ObservingFakeClock : FakeTimeProvider
{
    public int CreateTimerCalls { get; private set; }

    public override ITimer CreateTimer(
        TimerCallback callback,
        object? state,
        TimeSpan dueTime,
        TimeSpan period)
    {
        var inner = base.CreateTimer(callback, state, dueTime, period);
        CreateTimerCalls++;
        return inner;
    }
}
```

`NexusLabs.Testing.Time.RegistrationObservingTimeProvider` is that
shape, built out. It exists because the usual reason people reach
for an immediate timer — "my single `Advance` sometimes does not
fire the timer" — is a registration race, not a scheduler problem.
`FakeTimeProvider.Advance` only fires timers that are already
registered, so an advance that lands before the code under test
arms its delay leaves that timer due at a simulated time the test
never reaches. Waiting for the registration fixes the race;
replacing the scheduler hides it along with everything else.

## When the analyzer stays silent

- The class does not derive from `FakeTimeProvider`, directly or
  transitively. A custom `TimeProvider` subclass overriding
  `CreateTimer` is how you implement a clock, and is not reported.
- The class does not override `CreateTimer` at all. Subclasses that
  add labels, helpers, or other state are unaffected.
- The override calls `base.CreateTimer` anywhere in its body.

Delegation is checked syntactically: any `base.CreateTimer(...)`
call in the override exempts it. An override that delegates but
distorts the arguments it forwards — passing `TimeSpan.Zero` as the
due time, for example — is therefore **not** reported. That degree
of subversion is beyond what this rule attempts to detect.

## When suppression is the correct choice

An override that genuinely must replace the scheduler, with an
inline reason:

```csharp
#pragma warning disable NLF0028 // Deliberately models a platform timer that cannot be virtualised.
public override ITimer CreateTimer(/* ... */)
#pragma warning restore NLF0028
```

Or opt out per-project with
`dotnet_diagnostic.NLF0028.severity = none`.

# NLF0025 — Forward the available `TimeProvider`

**Severity:** Warning · **Category:** Usage · **Code-fix:** No

A call or construction that has an overload accepting
`System.TimeProvider`, made at a site where a clock is already
reachable but was not passed.

A type that takes a `TimeProvider` has declared that its timing is
controllable. A call inside that type which ignores the clock
silently opts back out: `Task.Delay(delay, cancellationToken)`,
`new CancellationTokenSource(delay)`, and
`new PeriodicTimer(period)` all bind to the machine clock, so the
behaviour they guard can only be exercised by a test that really
waits.

This is a common regression when a hand-rolled time abstraction is
replaced by the BCL one: the clock reads migrate cleanly, but a
custom `DelayAsync` wrapper has no direct BCL counterpart and gets
rewritten as a bare `Task.Delay`. The type still accepts a
`TimeProvider`, so nothing looks wrong, but the delay is no longer
controllable and the test that used to drive it now either sleeps
for real or is deleted.

## Bad — the clock is right there

```csharp
public sealed class RetryScheduler(TimeProvider timeProvider)
{
    public async Task RunAsync(CancellationToken cancellationToken)
    {
        // ❌ NLF0025 — timeProvider is in scope and was not passed.
        await Task.Delay(TimeSpan.FromMinutes(1), cancellationToken);

        // ❌ NLF0025 — constructions are covered too.
        using var attemptTimeout = new CancellationTokenSource(TimeSpan.FromSeconds(30));
        using var ticker = new PeriodicTimer(TimeSpan.FromSeconds(5));
    }
}
```

## Good — flow the clock

```csharp
public sealed class RetryScheduler(TimeProvider timeProvider)
{
    public async Task RunAsync(CancellationToken cancellationToken)
    {
        await Task.Delay(TimeSpan.FromMinutes(1), timeProvider, cancellationToken);

        using var attemptTimeout =
            new CancellationTokenSource(TimeSpan.FromSeconds(30), timeProvider);
        using var ticker = new PeriodicTimer(TimeSpan.FromSeconds(5), timeProvider);
    }
}
```

A test can then drive all three from one fake clock. See
`NexusLabs.Testing.Time` for advancing that clock without racing
the registration.

## What counts as "reachable"

The diagnostic message lists every name it found. A clock is
reachable when it is:

- a parameter of the enclosing method;
- an instance field or property on the enclosing type or any of its
  base types;
- a constructor parameter, including a primary constructor
  parameter.

**Static members are deliberately excluded.** Every type deriving
from `TimeProvider` inherits the static `TimeProvider.System`.
Treating that as "a clock is already available" would amount to
advising the author to bind to the machine clock, which is the
opposite of the rule's intent.

## When the analyzer stays silent

- The resolved call already takes a `TimeProvider`.
- No overload with a **strictly larger** parameter list accepts a
  `TimeProvider`. A shorter or equal-length overload is a different
  operation rather than the clock-aware form of the same one.
- No clock is reachable — [NLF0026](NLF0026.md) reports that case
  instead, at Info. The two rules are mutually exclusive, so a call
  site is never reported by both.

## When suppression is the correct choice

A call that must intentionally observe real time — a benchmark, or
a test that deliberately measures wall-clock behaviour:

```csharp
// Measures real scheduling latency; a virtual clock would defeat the point.
#pragma warning disable NLF0025
await Task.Delay(TimeSpan.FromMilliseconds(50), cancellationToken);
#pragma warning restore NLF0025
```

Or opt out per-project with
`dotnet_diagnostic.NLF0025.severity = none`.

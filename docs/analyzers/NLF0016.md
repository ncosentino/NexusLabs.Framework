# NLF0016 — HashSet&lt;string&gt; must use StringComparer.OrdinalIgnoreCase

**Severity:** Warning · **Category:** Usage · **Code-fix:** No

A `HashSet<string>` created without `StringComparer.OrdinalIgnoreCase`
(or created with any other comparer — `Ordinal`, `CurrentCulture`,
`CurrentCultureIgnoreCase`, `InvariantCulture`,
`InvariantCultureIgnoreCase`) uses the wrong default for the vast
majority of real-world string-set usages: it treats `"Foo"` and
`"foo"` as **different** keys.

The overwhelming majority of string-keyed sets are used for things
where case does not — and should not — matter: config keys, HTTP
header names, file/path names, environment variables, command names,
identifiers from external systems. NLF0016 makes the implicit
"the default comparer is wrong" choice visible at build time.

The rule fires on **`HashSet<string>` only** (not `HashSet<T>` for any
other `T`, and not `ImmutableHashSet<string>` which is a separate
type with different ergonomics). It checks:

- Every `new HashSet<string>(...)` overload (no args, capacity-only,
  `IEnumerable<string>`-only, with comparer arg)
- Target-typed `HashSet<string> s = new();`
- `Enumerable.ToHashSet(IEnumerable<string>)` and the overload that
  takes a comparer

## Bad — default comparer (case-sensitive)

```csharp
var headers = new HashSet<string>();
headers.Add("Authorization");
headers.Contains("authorization");   // false — different key

var configKeys = new HashSet<string> { "Database", "Cache" };

HashSet<string> seen = new();        // target-typed `new()` — same problem

var dedup = items.Select(x => x.Name).ToHashSet();    // IEnumerable<string>.ToHashSet
```

## Bad — explicit non-OrdinalIgnoreCase comparer

```csharp
var s = new HashSet<string>(StringComparer.Ordinal);                       // still case-sensitive
var s = new HashSet<string>(StringComparer.CurrentCulture);                // locale-dependent
var s = new HashSet<string>(StringComparer.InvariantCultureIgnoreCase);    // closer, but not Ordinal
```

## Good — explicit OrdinalIgnoreCase

```csharp
var headers = new HashSet<string>(StringComparer.OrdinalIgnoreCase);
headers.Add("Authorization");
headers.Contains("authorization");   // true

var configKeys = new HashSet<string>(StringComparer.OrdinalIgnoreCase)
{
    "Database",
    "Cache",
};

HashSet<string> seen = new(StringComparer.OrdinalIgnoreCase);

var dedup = items
    .Select(x => x.Name)
    .ToHashSet(StringComparer.OrdinalIgnoreCase);

// Constructor with both source and comparer:
var fromSource = new HashSet<string>(rawValues, StringComparer.OrdinalIgnoreCase);
```

## When the analyzer stays silent

- The HashSet is parameterised by any non-`string` `T` —
  `HashSet<int>()`, `HashSet<Guid>()`, `HashSet<MyEntity>()` — even
  if `MyEntity` has a string-backed equality. Only `HashSet<string>`
  triggers.
- `StringComparer.OrdinalIgnoreCase` is passed in any positional slot
  on the constructor or `ToHashSet` invocation.
- `ImmutableHashSet<string>` is a separate type with `Create` /
  `CreateRange` / `WithComparer` ergonomics. Out of scope for this
  rule.
- The `ToHashSet` call site has a source type other than
  `IEnumerable<string>` (i.e. the inferred return type is not
  `HashSet<string>`).

## When case-sensitivity is the correct choice (suppress per-call)

Some string-keyed sets genuinely need to be case-sensitive. The
expected suppression pattern is `#pragma warning disable NLF0016`
with an inline comment naming why case matters:

```csharp
// C# is a case-sensitive language; identifier names must compare
// case-sensitively or `myField` and `MyField` would collide.
#pragma warning disable NLF0016
var seenIdentifiers = new HashSet<string>(StringComparer.Ordinal);
#pragma warning restore NLF0016

// Cryptographic hash strings are case-canonical — case mismatch
// almost always means a bug, not a duplicate.
#pragma warning disable NLF0016
var seenHashes = new HashSet<string>(StringComparer.Ordinal);
#pragma warning restore NLF0016
```

For a project that operates entirely in a case-sensitive domain,
opt out per-project with
`dotnet_diagnostic.NLF0016.severity = none` in `.editorconfig`.

## Why not just require *some* comparer

Defaulting to "you must pass a comparer" without specifying which one
would let unsafe choices slip through:

- `StringComparer.Ordinal` looks safer than the default (it's
  explicitly culture-insensitive) but is still case-sensitive — it
  has every footgun the default has.
- `StringComparer.CurrentCulture` and `CurrentCultureIgnoreCase` are
  locale-dependent — the set you build under `en-US` may behave
  differently under `tr-TR` (Turkish dotted-i issue).
- `InvariantCulture` and `InvariantCultureIgnoreCase` are non-
  deterministic across .NET versions and run an unbounded culture
  table lookup that `Ordinal*` does not.

`OrdinalIgnoreCase` is the only choice that is both fast (byte-level
comparison, ASCII fast path) and locale-stable. The rule names it
specifically to push that choice as the default.

## Related rules

- The shipped Microsoft analyzer **CA1860** flags `.Count > 0` /
  `.Any()` on collections; orthogonal to NLF0016.
- The Microsoft analyzer **CA1851** warns about multiple enumerations
  of `IEnumerable`; the recommended `.ToHashSet(...)` fix interacts
  with NLF0016 — if your collection is strings, pass the comparer.
- **NLF0014** (specify `IFormatProvider` on `Parse`/`TryParse`) and
  NLF0016 share a theme: locale/culture-sensitive defaults are
  silent footguns and should be made explicit at call sites.

# NLF0014 — Specify IFormatProvider on Parse/TryParse when a culture-aware overload exists

**Severity:** Warning · **Category:** Usage · **Code-fix:** No

Calls to a type's static `Parse` or `TryParse` method without an explicit
`IFormatProvider` are silently culture-sensitive: the running thread's
`CurrentCulture` drives number formats, decimal separators, date layouts,
and other locale-dependent behavior. This is one of the most common
"works on my machine" bugs in .NET — code passes in development under
`en-US` and fails in production under `de-DE` (or vice versa) because of
a misplaced decimal separator or a swapped day/month.

NLF0014 makes the omission visible at build time wherever a culture-aware
upgrade path exists.

## Bad — implicit culture

```csharp
public decimal Read(string s) => decimal.Parse(s);          // NLF0014
public int Read(string s) => int.Parse(s);                  // NLF0014
public Guid Read(string s) => Guid.Parse(s);                // NLF0014
public DateTime Read(string s) => DateTime.Parse(s);        // NLF0014
public bool Read(string s, out int v) =>
    int.TryParse(s, out v);                                 // NLF0014
public int Read(string s) =>
    int.Parse(s, NumberStyles.Integer);                     // NLF0014 — has Styles but still no provider
```

## Good — explicit culture

```csharp
public decimal Read(string s) =>
    decimal.Parse(s, CultureInfo.InvariantCulture);

public int Read(string s) =>
    int.Parse(s, NumberStyles.Integer, CultureInfo.InvariantCulture);

public Guid Read(string s) =>
    Guid.Parse(s, CultureInfo.InvariantCulture);            // even though Guid ignores culture

public bool Read(string s, out int v) =>
    int.TryParse(s, NumberStyles.Integer, CultureInfo.InvariantCulture, out v);
```

For machine-readable input (IDs, configuration values, serialized
payloads, persisted data) use `CultureInfo.InvariantCulture`. For
human-facing input use the user's culture (typically
`CultureInfo.CurrentCulture` or a culture supplied by the request).

## Why stricter than CA1305

`CA1305` (Microsoft's "Specify IFormatProvider" rule, off by default in
modern .NET projects) exempts types whose parsing is currently
culture-insensitive. NLF0014 does not. The discipline of always being
explicit is more valuable than the inconsistency of skipping some calls
— and "currently insensitive" is a property of the BCL implementation
that can change between framework versions. If `Guid.Parse(string,
IFormatProvider)` exists, the rule wants to see the culture passed.

## How "compatible overload" is detected

The match is strict: a sibling overload qualifies as an upgrade target
only if it has

- the same method name,
- the same return type,
- `static` and `public`, and
- a parameter list that is **the called method's parameter list with
  exactly one additional `IFormatProvider` parameter inserted at any
  position** (matching by type and ref-kind in both directions).

Examples that do upgrade:

- `int.Parse(string)` upgrades to `int.Parse(string, IFormatProvider)`.
- `int.Parse(string, NumberStyles)` upgrades to
  `int.Parse(string, NumberStyles, IFormatProvider)`.
- `int.TryParse(string, out int)` upgrades to
  `int.TryParse(string, IFormatProvider, out int)`.

Examples that do **not** upgrade (rule stays silent):

- `bool.Parse(string)` — bool's `IParsable<bool>.Parse(string,
  IFormatProvider)` is an explicit interface implementation, not a
  public sibling overload.
- A user-defined `Parse(string)` whose only IFormatProvider sibling is
  `Parse(ReadOnlySpan<char>, IFormatProvider)` — different first
  parameter type, not a single-step upgrade.
- A `Parse(string)` whose only IFormatProvider sibling is
  `Parse(string, NumberStyles, IFormatProvider)` — two additional
  parameters, not a single-step upgrade; the caller would also have to
  decide on a `NumberStyles` value.

## When NOT to fire (the rule deliberately stays silent)

- The called overload already includes an `IFormatProvider` parameter
  (or any subtype, e.g. `CultureInfo`). The caller is being explicit at
  the API level, regardless of whether they pass `null` or a real
  provider at the call site.
- The called method is an instance method, an extension method, or a
  constructor. The rule only applies to `static` `Parse`/`TryParse`.
- The called method's containing type does not expose a compatible
  `IFormatProvider`-aware sibling overload.
- The current compilation does not reference `System.IFormatProvider`.

## When to suppress

The expected suppression pattern is `dotnet_diagnostic.NLF0014.severity
= none` at the project or repo level for short-lived scripts /
prototypes where culture-correctness is not a goal. For production
code there is no recommended suppression — the rule is intentionally
strict.

For an individual call site that cannot or should not be upgraded (for
example, code that explicitly mirrors a culture-implicit external
contract), use `#pragma warning disable NLF0014` with a comment
explaining why the implicit culture is the correct choice.

## Related rules

- [NLF0013](NLF0013.md) — When the called type is a strongly-typed ID
  wrapper that exposes its own `Parse`/`TryParse`, prefer that direct
  entry point over `new XxxId(BackingType.Parse(...))`. NLF0014 and
  NLF0013 compose: if you call `new XxxId(Guid.Parse(s))` you get
  NLF0013 (use `XxxId.Parse(s)`), and if you call `XxxId.Parse(s)`
  without a culture you get NLF0014 (specify a culture).
- **CA1305** (Microsoft NetAnalyzers) — the BCL equivalent. NLF0014 is
  the stricter superset: no per-type exclusions, only `Parse`/
  `TryParse` rather than the broader CA1305 scope.

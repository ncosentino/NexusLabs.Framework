# NLF0015 — Try-prefixed methods must return TriedEx&lt;T&gt;, TriedNullEx&lt;T&gt;, or Exception?

**Severity:** Warning · **Category:** Usage · **Code-fix:** No

A method whose name begins with `Try` (followed by an upper-case
character) must return one of the recognized "Try-result" shapes:

- `TriedEx<T>` / `Task<TriedEx<T>>` / `ValueTask<TriedEx<T>>`
- `TriedNullEx<T>` / `Task<TriedNullEx<T>>` / `ValueTask<TriedNullEx<T>>`
- `Exception?` / `Task<Exception?>` / `ValueTask<Exception?>`

The `Try` prefix is a load-bearing convention in this codebase: it
tells callers "this method swallows exceptions into a result object
you must inspect via `.Success` before reading `.Value`." A
`Try`-named method that returns `bool`, `T?`, `void`, etc. silently
breaks that contract — callers can no longer trust the prefix and
have to memorize per-method exception semantics.

NLF0015 makes the misuse visible at build time.

## Bad — Try prefix on a method that does not return a Try-result type

```csharp
public sealed class UserService
{
    // ❌ NLF0015 — returns Task<User?>, not Task<TriedEx<User>> / Task<TriedNullEx<User>>.
    public Task<User?> TryGetByIdAsync(UserId id) => /* ... */;

    // ❌ NLF0015 — BCL-style TryParse(out T). The Try prefix here means
    //              something different from everywhere else in the codebase.
    public bool TryParse(string raw, out User user) => /* ... */;

    // ❌ NLF0015 — returns void; nothing to inspect.
    public void TryDo() => /* ... */;
}
```

## Good — Try prefix matches the contract

```csharp
public sealed class UserService(ILogger<UserService> logger)
{
    // ✅ Returns Task<TriedEx<User>> — caller checks .Success then .Value / .Error.
    public Task<TriedEx<User>> TryGetByIdAsync(UserId id) =>
        Try.GetAsync(logger, async () =>
        {
            return await _repository.GetByIdAsync(id).ConfigureAwait(false);
        });

    // ✅ Returns Task<TriedNullEx<User?>> — null is a non-error success;
    //    exceptions still flow into .Error.
    public Task<TriedNullEx<User?>> TryFindByEmailAsync(string email) =>
        Try.GetOrNullAsync<User?>(logger, async () =>
        {
            return await _repository.FindByEmailAsync(email).ConfigureAwait(false);
        });

    // ✅ Returns Task<Exception?> — null = success, non-null = failure.
    public Task<Exception?> TryDeleteAsync(UserId id) =>
        Try.Async(logger, async () =>
        {
            await _repository.DeleteAsync(id).ConfigureAwait(false);
        });
}
```

## Good — rename the method when the return type is not a Try-result

If you genuinely want to return `bool`, `T?`, or another non-Try shape,
drop the `Try` prefix so the name accurately reflects the contract:

```csharp
public sealed class UserService
{
    // ✅ Was TryGetByIdAsync(Task<User?>) — now GetByIdAsync.
    public Task<User?> GetByIdAsync(UserId id) => /* ... */;

    // ✅ BCL-style parse without the convention's prefix.
    public bool ParseEmail(string raw, out string normalized) => /* ... */;
}
```

## When the analyzer stays silent

- The method is an `override`. The base declaration owns the name;
  fix it there. (If the base also violates the rule, the base
  declaration is flagged once.)
- The method is an interface implementation (implicit or explicit
  `T IFoo.Member()`). The interface declaration owns the name;
  fix it there.
- The method is declared on `NexusLabs.Framework.Try` itself. The
  static `Try` helper class is the convention's infrastructure —
  its members produce the Try-result types and are not subject to
  the rule.
- The method name is exactly `Try`, or `Try` followed by a lower-case
  character (e.g. `Trythis`). The prefix-detection requires an
  upper-case suffix character so the rule only fires on
  `Try`-followed-by-a-new-word.
- The method name contains an underscore (e.g.
  `TryGetAsync_NotFound_ReturnsNull`). The codebase uses
  underscore-delimited test naming
  (`MethodUnderTest_Scenario_Expectation`), where the first segment
  is the name of the SUT and the method is not itself an API
  expressing a Try-result contract. Production API methods follow
  PascalCase without underscores, so the underscore exclusion is a
  reliable signal that the name is a test method.

## How `TriedEx` / `TriedNullEx` are matched

Both type name AND containing namespace must match: the type must be
named `TriedEx` or `TriedNullEx` AND live in the
`NexusLabs.Framework` namespace. A type named `TriedEx` in some other
namespace does NOT satisfy the rule — the convention is specifically
about `NexusLabs.Framework`'s Try result shapes.

`Exception?` is matched as `System.Exception` (the `?` annotation is
not part of the symbol identity at the analyzer level).

## When to suppress

The expected suppression pattern is `dotnet_diagnostic.NLF0015.severity
= none` at the project or repo level for codebases that follow the BCL
`TryParse(out T) → bool` convention and have no intention of adopting
the `TriedEx<T>` result-type convention.

For an individual call site that mirrors an external BCL-style API
contract (e.g. implementing `IParsable<T>.TryParse`), use
`#pragma warning disable NLF0015` with a comment explaining why the
BCL-style prefix is intentional at that location.

## Related rules

- [NLF0029](README.md#nlf0029) — the independently configurable converse:
  result-returning methods must use a `Try` prefix. It checks nullable
  `Exception` explicitly and only exempts interface implementations when the
  contract belongs to another assembly.
- [NLF0002 / NLF0003](NLF0002.md) — once a method returns
  `TriedEx<T>` / `TriedNullEx<T>`, callers must check `.Success`
  before reading `.Value` / `.Error`. NLF0015 ensures the prefix only
  appears on methods that produce values those rules can govern.
- [NLF0009](NLF0009.md) — once a method declares it returns
  `Task<TriedEx<T>>`, its body must use `Try.GetAsync` (or
  pass-through to another `Try`-method) so the Task does not fault
  on uncaught exceptions. NLF0015 governs the name → return-type
  contract; NLF0009 governs the return-type → body contract.
- [NLF0006](NLF0006.md) — async methods whose entire body is a single
  try-catch should use `Try.Async` / `Try.GetAsync` /
  `Try.GetOrNullAsync` instead. Composes with NLF0015: rename to
  drop the `Try` prefix OR change the return type to a Try-result
  shape AND let NLF0006 push you toward the helper.

# NLF0013 — Use the strongly-typed ID's Parse/TryParse instead of constructing from a pre-parsed backing-type value

**Severity:** Warning · **Category:** Usage · **Code-fix:** No

Types decorated with `[StronglyTypedIds.StronglyTypedIdAttribute]` (from
[Andrew Lock's StronglyTypedId NuGet package](https://github.com/andrewlock/StronglyTypedId))
generate their own `Parse(string)` and `TryParse(string, out T)` static
methods that mirror the backing type's parsing API. Constructing the ID via
`new XxxId(BackingType.Parse(s))` or via
`if (BackingType.TryParse(s, out var v)) { var id = new XxxId(v); }` is an
awkward round-trip through the backing type — the strongly-typed ID can be
obtained directly with `XxxId.Parse(s)` or `XxxId.TryParse(s, out var id)`.

The diagnostic fires in two scenarios, both gated on (a) the constructed
type carrying `[StronglyTypedId]` and (b) the constructed type exposing the
corresponding `Parse(string)` / `TryParse(string, out T)` overload.

## Bad — Parse via backing type, then construct

```csharp
[StronglyTypedIds.StronglyTypedId]
public readonly partial struct OrderId { }

public OrderId Parse(string s) =>
    new OrderId(Guid.Parse(s)); // NLF0013: use OrderId.Parse(s)
```

## Good — Parse directly via the strongly-typed ID

```csharp
public OrderId Parse(string s) => OrderId.Parse(s);
```

## Bad — TryParse via backing type, then construct in the success branch

```csharp
public OrderId? TryParse(string s)
{
    if (Guid.TryParse(s, out var g))
    {
        return new OrderId(g); // NLF0013: use OrderId.TryParse(s, out var id)
    }
    return null;
}
```

## Good — TryParse directly via the strongly-typed ID

```csharp
public OrderId? TryParse(string s) =>
    OrderId.TryParse(s, out var id) ? id : null;
```

## When NOT to fire (the rule deliberately stays silent)

The TryParse arm is conservative to avoid silently changing semantics:

- The `TryParse` invocation is not the entire condition of an enclosing
  `if` (e.g. wrapped in `!`, joined by `&&` / `||`, used as a sub-expression
  of something larger).
- The construction lives outside the success branch (e.g. in the `else`,
  or after the `if` with a default-on-failure pattern).
- The out local is reassigned between its `out var` declaration and the
  construction — the rewritten `XxxId.TryParse(s, out var id)` would skip
  that intervening logic.
- The construction is inside a lambda or local function nested under the
  `if`'s success branch — capture semantics differ from the suggested
  rewrite.
- The constructed type does not expose its own `Parse(string)` or
  `TryParse(string, out T)` (e.g. `string`-backed IDs, or types with
  custom templates that suppress the parsing helpers).
- The backing-type parser is a different overload (e.g.
  `Guid.ParseExact(...)`, `int.Parse(string, NumberStyles)`,
  `Guid.Parse(string, IFormatProvider)`) — only the exact one-parameter
  `Parse(string)` and two-parameter `TryParse(string, out backingType)`
  overloads are matched in this version. Equivalent overloads on the
  strongly-typed ID would have to be verified individually before flagging.

The Parse arm only fires for direct `BackingType.Parse(string)` calls
nested as the sole constructor argument — the same constraints on overload
shape and target-type capability apply.

The rule is also silent if `StronglyTypedIds.StronglyTypedIdAttribute` is
not visible in the compilation (the package is not referenced from the
project being analyzed). In v1, the rule does not fall back to a
signature-based heuristic to catch IDs whose attribute was stripped from
referenced metadata via `[Conditional]` semantics.

## When to suppress

- The construction shape is intentional — for example, the backing-type
  parse result is needed for additional logging or normalization before
  the ID is constructed, and inlining `XxxId.Parse` would hide that step.
- The strongly-typed ID lives in a project that does not reference the
  `StronglyTypedId` attribute assembly, and the rewrite would require
  introducing that dependency.

Suppress via `dotnet_diagnostic.NLF0013.severity = none` in `.editorconfig`,
or via `#pragma warning disable NLF0013` at the call site.

## Related rules

- None — this rule stands alone. It does not interact with the Try-pattern
  family (NLF0002..NLF0009) or the disposable-aware analyzers (NLF0011,
  NLF0012, NLFSUP001).

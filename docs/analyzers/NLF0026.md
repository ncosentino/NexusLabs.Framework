# NLF0026 — Consider accepting a `TimeProvider`

**Severity:** Info · **Category:** Usage · **Code-fix:** No

A call or construction that has an overload accepting
`System.TimeProvider`, made at a site where **no** clock is
reachable.

This is the companion to [NLF0025](NLF0025.md). The statement
itself is not wrong — there is nothing to pass. What the rule
points at is the surrounding design: the enclosing method or type
does not accept a clock, so this timing can never be controlled by
a test.

It ships at **Info** rather than Warning because the fix is an API
change the analyzer cannot make on the author's behalf. Adding a
`TimeProvider` parameter ripples out to every caller, and that is a
decision for the author rather than the build.

## Reported

```csharp
public static class Backoff
{
    // ℹ️ NLF0026 — an overload takes a TimeProvider, but nothing here can supply one.
    public static Task PauseAsync() => Task.Delay(TimeSpan.FromMinutes(1));
}
```

## Resolved by accepting a clock

```csharp
public static class Backoff
{
    public static Task PauseAsync(TimeProvider timeProvider, CancellationToken cancellationToken)
        => Task.Delay(TimeSpan.FromMinutes(1), timeProvider, cancellationToken);
}
```

Once a clock is in scope, forgetting to pass it is reported by
[NLF0025](NLF0025.md) at Warning.

## Tuning the severity

In a codebase that has committed to injecting a clock everywhere,
promote it so the build enforces the design:

```ini
dotnet_diagnostic.NLF0026.severity = warning
```

Where real-time behaviour is intended throughout — an entry-point
executable, a benchmark project — silence it:

```ini
dotnet_diagnostic.NLF0026.severity = none
```

## When the analyzer stays silent

- The resolved call already takes a `TimeProvider`.
- No overload with a strictly larger parameter list accepts a
  `TimeProvider`.
- A clock **is** reachable — [NLF0025](NLF0025.md) reports that
  case instead, at Warning.

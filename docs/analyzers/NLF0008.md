# NLF0008 — Return exception from Try.Async callback instead of throwing

**Severity:** Warning · **Category:** Usage · **Code-fix:** No

`Try.Async` / `Try.GetAsync` / `Try.GetOrNullAsync` callbacks are expected
to either complete normally or **return a value that signals failure**.
A bare `throw` inside the callback bypasses the helper's caught-exception
contract and adds an unnecessary stack unwind.

## Bad

```csharp
var result = await Try.GetAsync(_logger, async () =>
{
    var user = await _repo.GetByIdAsync(id);
    if (user is null)
    {
        throw new InvalidOperationException("not found"); // do not throw here
    }
    return user;
});
```

## Good — return the exception

```csharp
var result = await Try.GetAsync(_logger, async () =>
{
    var user = await _repo.GetByIdAsync(id);
    if (user is null)
    {
        return new TriedEx<User>(new InvalidOperationException("not found"));
    }
    return user;
});
```

## Good — throw OUTSIDE the callback

```csharp
if (id <= 0)
{
    throw new ArgumentOutOfRangeException(nameof(id));
}

var result = await Try.GetAsync(_logger, async () => await _repo.GetByIdAsync(id));
```

## When suppression is legitimate

If the exception type intentionally must propagate (e.g. `OperationCanceledException`
that callers expect to bubble), throwing is correct — but in that case the
Try helper is the wrong abstraction.

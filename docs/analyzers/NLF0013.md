# NLF0013 — Use the strongly-typed ID's Parse/TryParse instead of constructing from a pre-parsed backing-type value

**Severity:** Warning · **Category:** Usage · **Code-fix:** No

Types decorated with `[StronglyTypedIds.StronglyTypedIdAttribute]` (from
[Andrew Lock's StronglyTypedId NuGet package](https://github.com/andrewlock/StronglyTypedId))
generate their own `Parse(string, ...)` and `TryParse(string, ..., out T)`
static methods that mirror the backing type's parsing API across every
overload — including `IFormatProvider`, `NumberStyles`, and so on.
Constructing the ID via `new XxxId(BackingType.Parse(s, ...))` or via
`if (BackingType.TryParse(s, ..., out var v)) { var id = new XxxId(v); }`
is an awkward round-trip through the backing type — the strongly-typed
ID can be obtained directly with `XxxId.Parse(s, ...)` or
`XxxId.TryParse(s, ..., out var id)`.

The diagnostic fires in two scenarios, both gated on (a) the constructed
type being recognised as a strongly-typed ID and (b) the constructed type
exposing the corresponding `Parse` / `TryParse` overload whose parameter
list matches the backing-type call being replaced.

## Bad — Parse via backing type, then construct

```csharp
[StronglyTypedIds.StronglyTypedId]
public partial struct OrderId { }

public OrderId Parse(string s) =>
    new OrderId(Guid.Parse(s)); // NLF0013: use OrderId.Parse(s)
```

## Good — Parse directly via the strongly-typed ID

```csharp
public OrderId Parse(string s) => OrderId.Parse(s);
```

## Bad — Parse with extra overload args (NumberStyles, IFormatProvider)

```csharp
public IntId ParseId(string s) =>
    new IntId(int.Parse(s, NumberStyles.Integer, CultureInfo.InvariantCulture));
    // NLF0013: use IntId.Parse(s, NumberStyles.Integer, CultureInfo.InvariantCulture)
    // (only fires if IntId.Parse(string, NumberStyles, IFormatProvider) exists)
```

## Bad — TryParse via backing type, then construct in the success branch

```csharp
public OrderId? TryParse(string s)
{
    if (Guid.TryParse(s, out var g))
    {
        return new OrderId(g); // NLF0013: use OrderId.TryParse(s, out var id)
    }
    return null;
}
```

## Bad — same as above with a predeclared local

```csharp
public OrderId? TryParse(string s)
{
    Guid g;
    if (Guid.TryParse(s, out g))
    {
        return new OrderId(g); // NLF0013: also flagged
    }
    return null;
}
```

## Good — TryParse directly via the strongly-typed ID

```csharp
public OrderId? TryParse(string s) =>
    OrderId.TryParse(s, out var id) ? id : null;
```

## When NOT to fire (the rule deliberately stays silent)

The TryParse arm is conservative to avoid silently changing semantics:

- The `TryParse` invocation is not the entire condition of an enclosing
  `if` (e.g. wrapped in `!`, joined by `&&` / `||`, used as a sub-expression
  of something larger).
- The construction lives outside the success branch (e.g. in the `else`,
  or after the `if` with a default-on-failure pattern).
- The local is reassigned anywhere inside the success branch — the
  rewritten `XxxId.TryParse(s, out var id)` would skip that intervening
  logic.
- The construction is inside a lambda or local function nested under the
  `if`'s success branch — capture semantics differ from the suggested
  rewrite.
- The constructed type does not expose a matching `Parse` / `TryParse`
  overload. The analyzer requires the parameter list of the ID's static
  parser to match the backing-type call exactly (with `out backingType`
  swapped to `out idType` for TryParse). If the ID was generated with
  a custom template that omits the matching overload, the rule stays
  silent.

## Detection of "strongly-typed ID"

The analyzer recognises a type as strongly-typed-ID-like by two paths:

1. **Attribute path** — the type carries
   `[StronglyTypedIds.StronglyTypedIdAttribute]`. This is the primary
   signal and works for any type defined in source.
2. **Structural fallback (cross-project only)** — when the type is
   defined in a different assembly than the one being compiled and does
   NOT carry the attribute (typically because
   `[Conditional("STRONGLY_TYPED_ID_USAGES")]` stripped it from
   metadata), a strict structural check is applied: the type must be a
   value type, defined outside `System.*` / `Microsoft.*` / `mscorlib` /
   `netstandard` (to exclude `DateTime`, `decimal`, etc.), the invoked
   constructor must be public and take a single parameter of the
   backing type, the type must expose a public instance property of
   that same backing type, and the type must expose a matching
   `Parse`/`TryParse` overload.

Source-defined types in the current project that do not carry the
attribute are **never** caught by the structural fallback — the
developer's decision to omit the attribute is respected.

## When to suppress

- The construction shape is intentional — for example, the backing-type
  parse result is needed for additional logging or normalization before
  the ID is constructed, and inlining `XxxId.Parse` would hide that step.
- The strongly-typed ID lives in a project that does not reference the
  `StronglyTypedId` attribute assembly, and the rewrite would require
  introducing that dependency.

Suppress via `dotnet_diagnostic.NLF0013.severity = none` in `.editorconfig`,
or via `#pragma warning disable NLF0013` at the call site.

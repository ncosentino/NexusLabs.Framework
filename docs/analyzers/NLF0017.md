# NLF0017 — Carter module must be declared `public sealed class`

**Severity:** Warning · **Category:** Usage · **Code-fix:** No

Any class that implements `Carter.ICarterModule` must be declared
`public sealed class`. Carter's reflection-based module-discovery
scan enumerates **only public types** that implement
`ICarterModule`; an `internal` (or `protected`, etc.) module
compiles cleanly but is silently skipped at application startup.
Every route the module declares returns 404 at runtime with no
build-time or startup-time signal to surface the
misconfiguration.

This silent failure mode — "the module exists in source, the build
succeeds, but the routes are not registered" — is one of the most
common Carter footguns. NLF0017 makes it a compile-time error
instead.

`sealed` is also required by convention: Carter modules are leaf
classes that own a route-registration block; subclassing them
creates duplicate route registrations and the resulting startup
behavior depends on the order Carter discovers types. Sealing the
modules eliminates that whole class of ambiguity.

## Bad — internal (or any non-public) module

```csharp
using Carter;
using Microsoft.AspNetCore.Routing;

// ❌ NLF0017 — Carter never registers this module; /thing returns 404.
internal sealed class ThingCarterModule : ICarterModule
{
    public void AddRoutes(IEndpointRouteBuilder app) =>
        app.MapGet("/thing", () => "ok");
}
```

## Bad — public but not sealed

```csharp
// ❌ NLF0017 — sealable but not sealed. A future class that derives
//              from this would create duplicate route registrations.
public class ThingCarterModule : ICarterModule
{
    public void AddRoutes(IEndpointRouteBuilder app) =>
        app.MapGet("/thing", () => "ok");
}
```

## Bad — public abstract base masquerading as a module

```csharp
// ❌ NLF0017 — Carter does not register abstract types either way,
//              but this declaration LOOKS like a registrable module.
//              If you genuinely need an abstract base, see the
//              suppression pattern below.
public abstract class CarterModuleBase : ICarterModule
{
    public abstract void AddRoutes(IEndpointRouteBuilder app);
}
```

## Good — public sealed class

```csharp
using Carter;
using Microsoft.AspNetCore.Routing;

// ✅ Carter discovers this and registers /thing as expected.
public sealed class ThingCarterModule : ICarterModule
{
    public void AddRoutes(IEndpointRouteBuilder app) =>
        app.MapGet("/thing", () => "ok");
}
```

## Good — sealed partial class

Partial declarations are aggregated by the compiler before the
analyzer inspects the symbol. As long as the combined declarations
yield `public sealed class`, the rule stays silent:

```csharp
// File 1
public sealed partial class ThingCarterModule : ICarterModule
{
    public void AddRoutes(IEndpointRouteBuilder app) => /* ... */;
}

// File 2
public sealed partial class ThingCarterModule
{
    private static IResult HandleThing() => /* ... */;
}
```

## When the analyzer stays silent

- The class does **not** implement `Carter.ICarterModule`. Same-
  named interfaces in other namespaces do not trigger the rule.
- The class is **already** declared `public sealed class`.
- The candidate is a `struct`, `record struct`, `interface`,
  `enum`, or `delegate` — only `class` declarations are checked.

## When suppression is the correct choice

The only legitimate reason to declare a Carter-related class as
something other than `public sealed class` is when it is an
intentional abstract base that other modules derive from. Carter
will not register the abstract base directly (no instance can be
constructed), so the routes-return-404 footgun does not apply, but
the rule still fires by default to keep "concrete module
accidentally non-public" the most visible signal.

Suppress per-class with `#pragma warning disable NLF0017` and a
comment naming the design intent:

```csharp
// Intentional base for shared module setup; Carter ignores abstract
// types so this declaration cannot create the "silently unregistered"
// footgun the rule guards against.
#pragma warning disable NLF0017
public abstract class CarterModuleBase : ICarterModule
{
    public abstract void AddRoutes(IEndpointRouteBuilder app);
}
#pragma warning restore NLF0017
```

For a project that does not use Carter (or uses a different
discovery mechanism), opt out with
`dotnet_diagnostic.NLF0017.severity = none` in `.editorconfig`.

## How the rule resolves `Carter.ICarterModule`

The analyzer matches purely by symbol metadata in the consumer's
compilation: it walks the candidate type's `AllInterfaces` and
checks each entry's `Name == "ICarterModule"` together with
`ContainingNamespace.ToDisplayString() == "Carter"`. No package
reference to Carter is required in the analyzer assembly. The
match also catches transitive implementation through a base class:
`public abstract class Base : ICarterModule` followed by
`internal sealed class Derived : Base` produces a diagnostic on
`Derived` (because the implementation is non-public) AND on `Base`
(because the abstract base is not sealed — see the suppression
section above for how to silence the base if it is intentional).

## Related rules

- The `.github/instructions/genesis/carter-modules.instructions.md`
  pattern document for this codebase states the same rule
  prose-form; NLF0017 enforces it at build time.
- Carter ships its own analyzer package (`Carter.Analyzers`) that
  validates route-registration shapes and handler signatures.
  NLF0017 complements those rules by enforcing the type-level
  visibility/sealing contract Carter's discovery depends on.
